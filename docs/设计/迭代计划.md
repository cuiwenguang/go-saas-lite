## 一、目标与边界

### 1.1 本次迭代目标

1. 修复已知缺陷（平台登录 refresh cookie）。
2. 套餐配额全部真正生效。
3. 文件存储可用：本地驱动 + 腾讯 COS + 阿里 OSS。
4. 手机号成为主标识，接入短信验证码；支持手机号登录与验证码重置密码。
5. 门户站点与自助注册。
6. 接入 asynq，提供异步任务与定时任务骨架。
7. 补齐 API 文档（OpenAPI + Swagger UI + 漂移检查）。
8. 补齐安全与数据缺口（强制改密、登录锁定、租户审计、配置初始化/缓存）。
9. 文档与验收闭环。

### 1.2 硬约束

- **单体、轻量**：不拆微服务，不引入服务网格。
- **不做**：CI/CD、Dockerfile、Compose、K8s、golangci-lint 流水线。
- **依赖克制**：新增依赖只用于明确能力（asynq、COS/OSS SDK、短信 SDK）。
- **不改变隔离模型**：继续使用「共享表 + `tenant_id` + Callback」，不做 Schema-per-tenant。

### 1.3 本次迭代不做

| 项目 | 说明 | 归属 |
| --- | --- | --- |
| 真实计费与支付 | 套餐价格、订单、微信/支付宝、发票、退款 | 下一迭代 |
| 数据导出 | CSV/Excel 导出、异步导出任务 | 下一迭代 |
| 邮件服务 | 邮件验证、邮件找回密码、邀请邮件 | 暂不做（国内以短信为主） |
| 图形验证码 | 滑块/点选验证码 | 暂不做（先用短信 + 限流） |
| Schema-per-tenant | 独立 Schema 模式 | 不做 |
| 多租户用户切换 | 一人多租户 | 不做（v1 一人一租户） |

### 1.4 下一阶段：台账 AI 业务平台

本次迭代交付的底座能力，直接被下一阶段使用：

- 文件存储 → 台账报表产物、用户上传的原始数据。
- asynq 定时任务 → 按用户/租户定时生成台账报表。
- 套餐配额 → 报表生成次数、存储空间、AI 调用量。
- 手机号 + 验证码 → 国内用户登录与找回密码。
- 门户 + 注册 → 业务平台自助开户。
- 计费与导出 → 在业务平台阶段落地。

## 七、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| `users.email` 改可空 | 登录、开通、重试、对账多处受影响 | 分步改：先迁移 + 索引，再改开通，再补测试；保留邮箱登录 |
| 短信通道审批周期 | 验证码无法真正下发 | 先上 `dev` 提供者；云适配器同步实现，配置即切换 |
| 注册被刷 | 产生大量空租户 | 同源校验 + IP 限流 + `auto_approve=false` 可选 + 蜜罐 |
| 文件配额并发超卖 | 多请求同时上传超限 | 按租户加 Redis 锁或 `SELECT ... FOR UPDATE` |
| asynq 重复执行 | 短信重复发送、文件重复删除 | 确定性 `TaskID` + 处理器幂等 |
| OpenAPI 与实现漂移 | 文档失真 | 路由漂移测试 + 文档随接口同 PR |
| COS/OSS SDK 体积 | 二进制变大 | 仅在使用时导入；本地驱动为默认 |
| 无 CI | 回归靠人工 | `go test ./...` + 手工回归清单；发布前固定执行 |

## 九、下一迭代：台账 AI 业务平台

### 9.1 计费

**目标**：套餐从「配额定义」升级为「可售卖商品」。

数据模型：

- `plan_prices(id, plan_code, cycle, currency, amount_cents, enabled)`
- `orders(id, tenant_id, plan_code, cycle, amount_cents, status, expires_at, paid_at, created_at)`
- `payments(id, order_id, provider, provider_txn_id, amount_cents, status, raw, created_at)`
- `invoices(id, order_id, tenant_id, title, tax_no, amount_cents, status, issued_at)`

流程：

1. 租户下单 → 创建 `orders(pending)`。
2. 调起微信/支付宝 → 支付回调 → 校验签名 → `payments(success)`。
3. 事务内：订单置 `paid` → 更新 `tenants.expire_at` → 写审计 `tenant.renew`。
4. 回调幂等：`provider_txn_id` 唯一。
5. 对账：按日拉取渠道流水，与 `payments` 比对。

### 9.2 导出

**目标**：查询结果可下载，大数据走异步。

数据模型：

- `export_jobs(id, tenant_id, type, status, file_key, error, created_at, finished_at)`

类型：

- 平台：租户列表、审计日志、用量报表。
- 租户：成员列表、台账报表。

流程：

1. `POST /exports` 创建任务并投递 asynq `export.generate`。
2. worker 生成 CSV 写入文件存储。
3. 前端轮询 `GET /exports/{id}`，完成后用签名 URL 下载。
4. 文件按保留期清理。

### 9.3 定时台账报表

**目标**：按用户配置的时间自动生成台账报表。

数据模型：

- `report_schedules(id, tenant_id, user_id, cron, timezone, template_id, enabled, next_run_at)`
- `report_jobs(id, schedule_id, tenant_id, user_id, status, file_key, error, started_at, finished_at)`

流程：

1. asynq Scheduler 或每分钟扫描 `next_run_at` 投递 `report.generate`。
2. 任务内重建 `Scope`，按模板生成报表，写入文件存储。
3. 记录 `report_jobs`，通知用户（站内信/短信/邮件按渠道能力）。
4. 失败重试，超过阈值告警。

### 9.4 其他后续能力

- 站内通知 / 消息中心。
- 事件总线与 outbox（如报表完成、支付成功）。
- AI 调用计量与配额（`ai_tokens` 指标）。
- 组织架构与数据权限（L2 数据范围）。
- 多租户用户切换（如需）。
